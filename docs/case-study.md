# 作品集案例：把“收藏夹吃灰”做成一条每日可跑的本地流水线

## 一句话

我没有再做一个收藏 App，而是把“收藏 → 提炼 → 日报 → 行动”拆成一条本地流水线：收藏夹里的新视频，第二天早上变成 Obsidian 里的知识卡和一份能读完的日报。

这个仓库是公开展示版：产品定义、架构、提示词、渲染器和合成示例公开；采集/登录层因为依赖个人会话和平台页面，保留在私有运行环境。

**我的角色**：产品定义、实现、验收和运维；AI 作为实现与运维的协作工具，产品判断和边界由我负责。

## 背景

收藏动作很便宜，回看很贵。

刷到一条讲工具、方法或案例的视频，点收藏只需要一秒；真正坐下来回看，需要重新找到它、判断值不值得看、再从口播里提取可执行的动作。结果是收藏夹越来越长，真正进入工作和知识库的内容越来越少。

现有方案通常要求再装一个 App、再登录一个账号、再订阅一个服务。但我需要的不是另一个客户端，而是一条**在我自己的电脑上运行、能接到 Obsidian 和本地通知、失败时我能修**的流水线。

## 约束

这个项目从一开始就不是“做一个通用产品”：

- **单人使用**：只有一个用户，不需要账号体系、多租户、权限。
- **本地优先**：登录态、视频、OCR 都在本机；不把个人会话交给第三方。
- **模型可替换**：脚本不绑定某个模型 API；分析由宿主按提示词完成。
- **可维护**：每一步能单独重跑，失败能定位，输出是普通文件。
- **有边界**：只读采集，不做点赞/关注/评论/发布，不绕过验证码。
- **公开有取舍**：公开展示产品判断和可运行渲染层，不公开登录态和采集器。

## 我做了什么

### 1. 先把问题拆成状态机

不是“写个爬虫下载视频”，而是先定义一条链路和它的失败分支：

```text
未处理 → 采集中 → 已下载 → 已抽帧/OCR → 已分析 → 已渲染 → 已推送
              ↘ 登录失效
              ↘ 单条失败
              ↘ 分析缺条
              ↘ 渲染失败
```

每个状态都有落盘记录，所以重跑不会重复处理，失败不会拖垮整批。

### 2. 把“模型”从采集器里拿出去

采集器只负责拿到证据：标题、描述、时长、字幕/OCR、带时间戳的文本。它不调用模型，也不决定“值不值得看”。

分析由宿主按 [prompts/analyze.md](../prompts/analyze.md) 完成，输出严格 JSON：`summary`、`hook`、`verdict`、`actions`、`followup`、`confidence`、`evidence`。这样模型可以换，输出可以人工检查，失败可以只重跑分析。

### 3. 让输出真的会被看

知识卡不是“视频摘要”，而是五个能直接决策的字段：

- 讲了什么
- 钩子（尽量带秒数）
- 值不值（值得完整看 / 只看前半 / 看个乐 / 跳过）
- 能抄什么（1–3 条动词开头的动作）
- 要不要跟进

日报再按“值不值 → 置信度 → 可执行动作数 → 是否要跟进”排 Top 3，而不是把所有条目平铺。

### 4. 把失败当成一等公民

第一版就处理了这些情况：

- 登录过期 → 停止，不生成空结果；
- 单条下载/抽帧失败 → 记录，继续下一条；
- 模型漏条 → 渲染校验，进入 `invalid`，不静默生成空卡片；
- 用户改过卡片状态 → 不覆盖，写 `.regen.md`；
- 同日重复运行 → 按日合并，不重复出卡。

## 关键取舍

| 选择 | 放弃什么 | 换来什么 |
| --- | --- | --- |
| 专用 Chrome + 持久会话 | 多一个窗口、依赖本机 Chrome | 登录态跨天复用，定时任务可无人值守 |
| OCR 优先，不接 ASR | 口播为主的内容效果有限 | 不引入额外服务/费用/隐私评估，MVP 能跑 |
| JSON + Markdown，不上数据库 | 复杂查询和并发能力 | 可直接检查、手工修复、无迁移负担 |
| 模型与采集解耦 | 不能“一条命令全自动” | 模型可替换，失败可单独重跑 |
| 公开渲染层，私有采集层 | 不能承诺一键复现 | 展示产品判断，同时守住账号与平台边界 |

## 结果

- **M1 单条闭环**：一条视频生成源笔记、知识卡、日报记录。
- **M2 批量与去重**：`--limit 10` 跑通，成功 9 条、失败 1 条（ffmpeg 抽帧超时）；同日重复运行按日合并。
- **M3 每日 08:00 + 通知**：定时任务已落地；最终回复为日报摘要。
- **M4 历史回填**：未开始，先保证每日增量稳定。

失败样本没有被隐藏：它进入日报的“失败 / 待处理”区。这比“成功率 100%”的截图更能说明系统能被维护。

## 如果重来

1. **更早做一次真实回放**：先用 3 条不同形态的视频（口播、图文、教程）验证 OCR 上限，再决定要不要 ASR。
2. **更早定义“成功”**：不是“生成了卡片”，而是“我一周内真的打开了其中几条”。这需要产品指标，不只是工程指标。
3. **更早把状态文件当接口**：`last_run.json` / `last_render.json` 现在是排障入口，应该从第一版就设计成稳定契约。

## 这个项目证明了什么

- 能把一个模糊的“收藏夹吃灰”拆成可验收的流程、字段和失败分支；
- 能在隐私、平台边界和可用性之间做取舍，而不是先堆功能；
- 能让 AI 参与实现，但把产品判断、验收和边界留在人这边；
- 能把一次性脚本整理成有文档、有状态、可交接的长期工具。

## 适合谁看

如果你在招 **B 端产品、AI 应用、FDE / 行业解决方案** 方向的人，这个案例能说明：

- 我如何从真实摩擦里定义问题；
- 我如何把模型能力放进一条可运维的链路，而不是做一个 demo；
- 我如何处理失败、隐私和长期维护。
